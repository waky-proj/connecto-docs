# S6 local acceptance and agreement implementation

6 October 2026, Pacific/Auckland. This records local code and tests, not release acceptance or deployment.

The API accepts a pending request only from the Offering owner, with the current request revision and an idempotency key. It checks both listings' current revisions and published states, server-derived participants, mutual blocks and one agreement per Need. SQL Server acceptance runs in a serializable transaction and the generated AddAgreements migration creates unique NeedId and ConnectionRequestId indexes. The request transition and Engagement insert use one SaveChanges operation. The Engagement copies titles, terms, NZD price basis/amount, listing revisions and participants at acceptance. Participant-only agreement routes serve this saved copy after listing edits. A sequential retry with the same key and revision returns the same agreement; a changed revision/key conflicts. The React inbox offers Accept terms to the recipient, shows saved agreement terms, refreshes server state and clears private state on session reset.

Verification: 43 backend tests passed, one opt-in SQL acceptance test skipped; 50 frontend tests passed; frontend lint and production build passed. Backend API tests use EF InMemory and synthetic signed JWTs. The S6 test covers role denial, outsider access, validation, retry, capacity and a snapshot after a listing title edit. The frontend test covers authenticated accept and agreement routes. The AddAgreements migration was generated and inspected for unique indexes but not applied to SQL Server. No actual SQL concurrent acceptance or restart test, real Cognito multi-account browser, accessibility or staging check was run. One agreement per Need is a local implementation invariant pending an explicit release capacity and cancellation policy decision. S6 release acceptance remains open.
